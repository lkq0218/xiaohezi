# 电力服务智能客服系统提升方案

## 一、项目当前阶段与核心问题

当前系统已经完成前端交互、后端业务接口、权限认证、数据持久化、RAG、LLM 接入、敏感操作确认、异常处理、监控与部署等完整工程链路，能够完成电费查询、缴费、报修、知识问答等业务。

但从“数字管理研发工程师”的要求来看，当前系统仍主要解决的是：

> **如何正确执行一个已经确定的业务流程。**

例如用户提出缴费请求后，系统按照固定代码完成参数收集、查询欠费、二次确认和业务办理。

而企业数字化系统更核心的问题是：

> **面对不同业务条件，系统为什么做出某个判断？判断规则能否被定义、修改、验证和持续优化？**

因此项目下一阶段不再重点增加业务功能，而是围绕 **业务规则数字化、决策自动化、过程可解释和结果可验证** 进行升级。

---

# 二、提升方向一：将散落在业务代码中的判断逻辑抽象为业务规则

## 1. 当前问题

目前缴费、报修等业务中的判断主要直接写在 Service 层代码中，例如：

* 是否缺少必要参数；
* 是否需要二次确认；
* 当前业务状态是否允许执行；
* 是否属于当前用户资源；
* 是否重复提交；
* 不同异常应该如何处理。

这种方式在业务规模较小时没有问题，但随着业务规则增加，会产生两个问题：

第一，**业务规则和程序执行逻辑耦合**。

例如：

```java
if (amount > 500) {
    requireConfirmation();
}
```

这里同时包含了：

* “500 元以上属于需要确认的业务”这一业务规则；
* “触发确认流程”这一系统动作。

未来如果业务部门希望将 500 元调整为 1000 元，或者不同用户采用不同阈值，就必须修改代码。

第二，无法清晰回答：

> 系统为什么做出了这次决策？

---

## 2. 提升方法

增加独立的 **Business Rule Engine（业务规则层）**，将业务条件、判断结果和后续动作进行结构化表达。

定义统一规则模型：

```text
Rule
├── ruleId
├── ruleName
├── scene
├── condition
├── priority
├── decision
├── reason
└── version
```

例如缴费规则：

```text
规则：PAYMENT_CONFIRM_001

条件：
amount >= 500

决策：
REQUIRE_CONFIRMATION

原因：
大额缴费需要用户二次确认
```

停电报修可以定义：

```text
规则：OUTAGE_REPORT_002

条件：
同一户号存在未完成报修工单

决策：
REJECT_DUPLICATE

原因：
避免重复创建报修工单
```

业务执行流程调整为：

```text
用户请求
   ↓
IntentResolver
   ↓
业务参数提取
   ↓
Business Context
   ↓
Rule Engine
   ↓
Decision
   ↓
业务执行 / 二次确认 / 转人工 / 拒绝
```

---

## 3. 为什么选择这种方法

因为企业数字化系统真正需要沉淀的并不是某一段 Java 代码，而是：

> **业务专家进行判断时使用的条件和规则。**

规则层能够把原本隐藏在 Service 代码中的判断逻辑显式化，使业务逻辑具备：

* 可阅读；
* 可修改；
* 可测试；
* 可解释；
* 可版本管理；

的能力。

这与数字管理岗位所要求的：

> “将模糊的业务直觉和隐藏在经验中的判断规则转化为清晰、可验证、可运行的代码与算法”

直接对应。

---

# 三、提升方向二：从“业务流程”进一步抽象出统一决策模型

## 1. 当前问题

现在系统针对不同业务分别编写 Service，例如：

```text
PaymentService
OutageService
BillingService
```

每个业务内部都有自己的判断逻辑。

但从数字化管理角度看，这些业务实际上存在相同的决策模式：

```text
获取业务信息
↓
判断条件
↓
产生决策
↓
执行动作
```

如果每增加一个业务都重新实现一套判断流程，系统很难形成可以复用的数字决策能力。

---

## 2. 提升方法

增加统一的 **Decision Engine**。

定义：

```text
DecisionContext
```

记录一次决策所需要的信息，例如：

```json
{
  "userId": "U001",
  "scene": "PAYMENT",
  "amount": 680,
  "accountStatus": "NORMAL",
  "hasPendingPayment": false
}
```

规则系统输入 DecisionContext 后输出：

```json
{
  "decision": "REQUIRE_CONFIRMATION",
  "ruleId": "PAYMENT_CONFIRM_001",
  "reason": "payment_amount >= 500"
}
```

系统根据 Decision 类型统一执行：

```text
ALLOW
→ 自动办理

REQUIRE_CONFIRMATION
→ 用户二次确认

MANUAL_REVIEW
→ 转人工

REJECT
→ 拒绝操作
```

---

## 3. 为什么选择这种方法

这样可以将：

> “某一个业务怎么写”

提升为：

> “系统如何处理一类业务决策”。

以后无论新增：

* 更名过户；
* 业务报装；
* 欠费处理；
* 异常账单申诉；

都可以复用同样的决策框架。

这能够体现系统设计中的**抽象能力和可扩展性**，同时对应岗位要求中的：

> 将业务目标和规则体系转化为系统功能、数据模型与自动化逻辑。

---

# 四、提升方向三：增加 Human-in-the-loop，而不是让 AI 直接决定所有业务

## 1. 当前问题

LLM 擅长：

* 理解自然语言；
* 判断用户意图；
* 提取非结构化信息；
* 生成解释。

但并不适合直接负责：

* 缴费；
* 报修；
* 权限判断；
* 高风险业务操作。

如果让模型直接决定业务执行，一旦模型产生错误判断，风险较高。

---

## 2. 提升方法

建立基于 **业务风险 + 模型置信度** 的分级处理机制：

```text
请求
 ↓
LLM / Rule Engine
 ↓
风险判断
 ↓

低风险 + 高置信度
→ 自动处理

中风险
→ 用户确认

高风险 / 低置信度
→ 人工审核
```

例如：

| 场景     | 处理方式 |
| ------ | ---- |
| 查询电价   | 自动执行 |
| 查询本人账单 | 自动执行 |
| 小额模拟缴费 | 二次确认 |
| 大额缴费   | 强制确认 |
| 户号归属异常 | 禁止执行 |
| 意图无法确定 | 转人工  |

现有的 action token 二次确认机制可以直接作为 Human-in-the-loop 的基础能力，而不是重新建设一套系统。

---

## 3. 为什么选择这种方法

企业数字化的目标并不是：

> “所有事情都让 AI 做。”

而是：

> **明确哪些事情可以自动化，哪些判断必须由人保留最终控制权。**

因此选择“规则 + AI + 人工”的组合，而不是完全依赖大模型。

这种设计既能够利用 AI 提升自动化程度，又能够保证敏感业务的可靠性。

---

# 五、提升方向四：将 traceId 升级为“业务决策 Trace”

## 1. 当前问题

目前 traceId 主要用于：

> 一个接口报错之后能够定位日志。

这属于典型的软件工程 Trace。

但企业数字化系统还需要回答：

> 为什么系统做出了这个业务判断？

例如用户询问：

> 为什么我的缴费没有直接执行？

仅知道接口调用链并不足够。

---

## 2. 提升方法

在现有 traceId 基础上增加 Decision Trace，记录：

```text
decisionId
traceId
userId
scene
input
matchedRules
ruleVersion
modelResult
finalDecision
executionResult
timestamp
```

例如：

```text
Decision ID：D20260818001

业务：
模拟缴费

金额：
680 元

匹配规则：
PAYMENT_CONFIRM_001

规则：
amount >= 500

决策：
REQUIRE_CONFIRMATION

执行结果：
用户确认后缴费成功
```

这样系统不仅可以知道：

> 系统执行了什么。

还可以知道：

> 系统为什么这么执行。

---

## 3. 为什么选择这种方法

企业管理系统中的自动决策必须具备可解释和可追溯能力。

尤其当业务规则不断调整时，只有记录：

> 输入 → 规则 → 判断 → 动作 → 结果

才能分析错误来自：

* 数据；
* 模型；
* 规则；
* 系统执行；

中的哪一环。

这比传统技术日志更符合业务数字化场景。

---

# 六、提升方向五：基于历史 Trace 实现 Replay 和规则验证

## 1. 当前问题

假设业务部门提出：

> “500 元以上必须二次确认”太严格，希望调整到 1000 元。

如果直接修改线上规则，就无法知道：

> 新规则会对历史业务产生什么影响。

规则变化仍然依赖经验。

---

## 2. 提升方法

增加 Decision Replay 功能。

将历史 DecisionContext 保存下来：

```text
历史请求
↓
旧规则 V1
↓
历史结果
```

当规则调整时：

```text
历史请求
↓
新规则 V2
↓
模拟结果
```

比较：

```text
             V1        V2

自动处理率    63%       78%

确认率        32%       17%

转人工率      5%        5%
```

进一步观察：

> 哪些历史请求因为新规则改变了决策？

例如：

```text
500~1000 元缴费

旧规则：
需要确认

新规则：
自动办理
```

从而在正式发布规则之前评估影响。

---

## 3. 为什么选择这种方法

业务规则本质上也是一种“算法”。

算法调整不能只依赖：

> “我觉得这样会更好。”

而应该做到：

> **历史数据验证 → 比较结果 → 再决定是否上线。**

Replay 可以让业务经验逐渐从：

> 人的直觉

变成：

> 数据验证后的规则。

这一点尤其符合数字管理岗位强调的：

> **可量化、可验证。**

---

# 七、提升方向六：建立面向业务结果的评估指标

## 1. 当前问题

目前项目主要使用：

* 接口测试；
* 单元测试；
* 健康检查；
* Prometheus；

验证系统是否正常工作。

这些指标能够回答：

> 系统有没有出故障？

但无法回答：

> 系统设计是否真的改善了业务流程？

---

## 2. 提升方法

增加业务决策评估指标。

核心指标可以包括：

### 自动处理率

```text
自动完成业务数 / 总业务请求数
```

用于判断系统减少了多少人工操作。

### 人工介入率

```text
人工处理业务数 / 总请求数
```

观察系统对人工经验的依赖程度。

### 规则命中率

统计：

```text
PAYMENT_CONFIRM_001     327 次
OUTAGE_DUPLICATE_002    86 次
```

识别最常触发的业务判断。

### 决策修改率

统计系统推荐后被人工修改的比例：

```text
人工修改决策数 / 系统决策数
```

这是衡量决策质量的重要指标。

### 自动化成功率

```text
成功自动完成请求 / 自动处理请求
```

防止为了追求自动化率而降低业务质量。

---

## 3. 为什么选择这种方法

数字化项目最终不能只证明：

> 系统上线了。

而应该回答：

> 系统到底减少了多少人工判断？
> 哪些业务最适合自动化？
> 哪些规则需要继续修改？

建立业务指标以后，项目才形成：

```text
发现问题
↓
建立规则
↓
系统执行
↓
数据反馈
↓
规则优化
```

这一完整闭环。

---

# 八、最终形成的系统架构

升级后的系统不再只是：

```text
Vue
 ↓
Spring Boot
 ↓
LLM / RAG
 ↓
业务接口
```

而形成：

```text
                    用户请求
                       ↓
                Intent Resolver
                       ↓
               Business Context
                       ↓
          ┌────────────┴────────────┐
          ↓                         ↓
     Rule Engine                 LLM / RAG
   确定性业务规则             非结构化理解与知识
          └────────────┬────────────┘
                       ↓
                 Decision Engine
                       ↓
          ┌────────────┼────────────┐
          ↓            ↓            ↓
       自动执行       二次确认      人工处理
          ↓
                 Business Service
                       ↓
                     MySQL
                       ↓
                Decision Trace
                       ↓
               Replay / Evaluation
                       ↓
                  规则持续优化
```

整个项目由原来的：

> **AI 客服功能实现**

进一步升级为：

> **业务问题建模 → 规则数字化 → 系统自动决策 → 人工兜底 → 决策追踪 → 数据验证 → 规则迭代**

---

# 九、建议实施顺序

不建议一次把所有功能全部实现，可以按照以下顺序推进。

## P0：业务规则抽象

首先选择两个已有场景：

* 模拟缴费；
* 停电报修。

将现有 Service 中的关键判断抽成 Rule Engine。

这一阶段重点证明：

> **我能够把业务逻辑抽象成结构化规则。**

---

## P1：Decision Engine + Decision Trace

统一定义：

```text
DecisionContext
RuleResult
Decision
DecisionTrace
```

完成：

> 输入 → 判断 → 决策 → 执行 → 日志

完整链路。

这一阶段重点证明：

> **我能够把业务规则转化成系统架构。**

---

## P2：Replay + Evaluation

保存历史决策输入，并提供规则版本 Replay。

输出：

* 自动处理率；
* 确认率；
* 人工介入率；
* 不同规则版本差异。

这一阶段重点证明：

> **我的方案不是凭经验修改，而是能够用数据进行验证。**

---

## P3：Human-in-the-loop 与规则配置化

最后再进一步完善：

* 人工审核；
* 规则启停；
* 规则版本；
* 阈值配置；
* 决策反馈。

从而形成完整的业务决策管理能力。

---

# 十、项目升级后的核心能力总结

完成以上升级后，这个项目可以重点体现四种能力：

### 1. 定义问题

不是简单实现“缴费功能”，而是分析：

> 哪些条件决定一笔业务能否自动办理。

### 2. 抽象业务

把工作人员原本依赖经验进行的判断转变为：

```text
输入条件 + 业务规则 + 决策结果
```

### 3. 设计系统

将规则进一步映射为：

* 数据模型；
* Rule Engine；
* Decision Engine；
* Human-in-the-loop；
* Trace；
* Replay。

### 4. 验证效果

通过历史数据和业务指标验证：

> 规则修改是否真正提升自动化水平，同时没有引入额外风险。

最终形成：

> **发现问题 → 拆解问题 → 抽象规则 → 设计系统 → 实现功能 → 数据验证 → 持续迭代**

的完整数字化建设闭环。
