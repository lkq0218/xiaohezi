# 多模态电力服务助手设计

> 状态：规划中。本文描述下一阶段设计，不代表功能已经实现。只有通过对应验收门禁后，能力才可写入 README 或简历。

## 1. 目标与取舍

本阶段不重写现有系统，而是在 Spring Boot 电力服务 Agent 上增加图片、语音和图像生成能力。项目首先证明一条完整链路：用户上传账单图片，系统安全保存文件，提取字段，用 Java 规则和已有账单数据校验，再生成带依据的解释。

优先级按业务价值和风险排列：

1. 账单图片理解：最适合复用现有账单查询、解释和确定性计算。
2. 故障图片辅助报修：只描述可见现象，不诊断、不指导高风险维修。
3. 多模态知识问答：检索政策文字、流程图、操作截图和设备图片，并引用证据。
4. 语音交互：ASR 产出的文本复用现有 Agent，TTS 只负责播报最终文本。
5. 图像生成：用于安全宣传图和解释卡片，不参与事实判断或业务证据链。

本期明确不做模型预训练、不把所有服务拆成微服务、不接真实电网或支付系统，也不承诺实时视频诊断。个人作品首先追求边界清楚、可以运行、可以复现实验。

## 2. 核心原则

### 2.1 模型负责感知，程序负责事实与动作

- OCR/VLM 提取图片中“看到了什么”，并返回符合 JSON Schema 的候选字段、置信度和证据区域。
- Java 负责金额类型转换、账期检查、分项求和、数据库对账、权限校验、幂等和状态迁移。
- 图片中的文字始终是不可信数据，不能成为系统指令，不能直接触发缴费、报修或工具调用。
- 低置信度、字段冲突和模糊图片进入 `NEEDS_REVIEW`，不得用语言流畅度掩盖不确定性。
- 所有有副作用的业务仍经过“生成草稿 → 用户确认 → 幂等提交”。

### 2.2 生成内容与事实证据隔离

AI 生成图片必须标记“AI 生成”，保存模型、提示词、版本和生成时间。生成图片不能作为账单、缴费、现场故障或知识库事实的证据，也不能反向进入评测集的真实样本区。

## 3. 总体架构

```text
Vue Web
  ├─ 文本 / 图片上传 / 录音
  └─ 预览、纠错、证据引用、动作确认
          │
Spring Boot（认证、编排、确定性业务）
  ├─ MediaService：类型/大小/所有权校验、对象存储
  ├─ MultimodalOrchestrator：任务状态与超时
  ├─ BillImageService：提取、归一化、Java 规则对账
  ├─ FaultImageService：质量门禁、安全门禁、报修草稿
  ├─ MultimodalRagService：文字/图片混合召回与引用
  ├─ SpeechService：ASR/TTS 适配
  └─ ImageGenerationService：隔离的异步创作任务
          │
  ├─ MySQL：元数据、分析结果、任务、审计
  ├─ Redis：短期任务状态、限流、缓存
  ├─ MinIO/S3：原图、缩略图、音频、生成图
  └─ 模型适配器：OCR、VLM、ASR、TTS、Embedding、图像生成
```

保持模块化单体作为主架构。MVP 直接由 Java 调用托管模型；需要学习本地模型部署时，再增加 Python 推理侧车，Spring Boot 仍是唯一业务入口。不要为了展示“微服务”提前增加分布式复杂度。

## 4. 领域模型与存储

二进制内容进入对象存储，数据库只保存元数据和结构化结果。禁止把 Base64 原图写入业务表或日志。

### 4.1 建议新增表

| 表 | 关键字段 | 作用 |
| --- | --- | --- |
| `media_asset` | `id, owner_id, object_key, media_type, mime_type, size_bytes, sha256, status, expires_at, version` | 文件所有权、生命周期和乐观锁 |
| `processing_job` | `id, asset_id, job_type, status, attempt, error_code, started_at, finished_at` | 可恢复的异步任务 |
| `multimodal_analysis` | `asset_id, model, prompt_version, schema_version, result_json, confidence, latency_ms, token_usage` | 可追溯的模型结果 |
| `bill_extraction` | `account_no_masked, billing_period, amount, field_confidence_json, validation_status` | 账单候选字段与校验状态 |
| `fault_observation` | `relevance, quality, visible_symptoms_json, risk_level, safety_rule_hits` | 可见现象与安全门禁结果 |
| `knowledge_asset` | `source_uri, title, version, page_no, region_json, ocr_text, caption, embedding_ref` | 图文知识证据 |
| `generated_asset` | `prompt, model, model_version, seed, review_status, watermark_status` | 生成内容溯源 |

`media_asset.status` 建议使用：`UPLOADED → VALIDATED → PROCESSING → READY`，异常进入 `REJECTED/FAILED`，超过保留期进入 `EXPIRED`。任务以数据库为恢复事实源，Redis 只做加速；服务重启后扫描未完成任务并按重试上限恢复。

### 4.2 文件安全与隐私

- 服务端同时检查扩展名、声明 MIME 和文件魔数；限制文件大小、像素总量、页数、音频时长和每用户频率。
- 对象键使用系统生成 UUID，不使用原文件名拼路径；下载必须校验资源所有者或管理员角色。
- 删除 EXIF/GPS 元数据，生成安全缩略图；生产方案加入恶意文件扫描。
- 日志只记录 `assetId`、状态、耗时和错误码，不记录户号、原始 OCR 文本、图片或音频。
- 演示数据默认 7 天过期；评测样本必须脱敏并单独版本管理。真实保留期需由隐私政策确定。

## 5. API 与前端交互

MVP 使用后端接收 multipart 上传，单图上限由项目配置（建议 10 MB），以后再演进为预签名直传。

```http
POST /api/media                         # 上传，返回 assetId/status
GET  /api/media/{assetId}               # 查询元数据和处理状态
POST /api/media/{assetId}/analyses      # BILL/FAULT/SCREENSHOT
GET  /api/media/{assetId}/analyses/latest
POST /api/audio/transcriptions          # 批量 ASR
POST /api/speech                         # 文本转语音
POST /api/image-generations              # 隔离的异步生成任务
GET  /api/jobs/{jobId}
```

现有消息接口保持兼容，并增加附件引用而不是传 Base64：

```json
{
  "message": "帮我解释这张账单",
  "clientRequestId": "uuid",
  "attachments": [
    {"assetId": "uuid", "purpose": "BILL"}
  ]
}
```

后端在进入 Agent 前检查资源所有权、状态、用途和数量。前端需要提供上传进度、预览、识别中、可编辑的提取结果、冲突原因和重新拍摄提示；用户修正值与模型原值分开保存，便于审计和评测。

## 6. 关键业务流程

### 6.1 账单图片理解

```text
上传与安全校验
 → 图片质量判断
 → OCR/VLM 按 Schema 提取字段和证据区域
 → Java 归一化（日期、金额、单位、掩码）
 → Java 规则校验（字段完整性、分项求和、账期）
 → 与当前登录用户的演示账单对账
 → VERIFIED / CONFLICT / NEEDS_REVIEW
 → 生成解释，不修改账单事实
```

关键字段包括户号（展示时脱敏）、账期、应缴金额、已缴金额、截止日期、用电量和分项金额。金额必须用 `BigDecimal`，不得让模型执行最终计算。图片结果只作为候选输入，不能直接覆盖数据库账单。

建议先以 VLM 结构化输出完成 MVP，再接入独立 OCR 作为对照基线。两者不一致时由规则与人工确认裁决，而不是再次让模型“猜一个”。

### 6.2 故障图片辅助报修

流程先判断图片是否相关、是否足够清晰，再提取“可见现象”，例如外壳破损、疑似烟雾、线路垂落；不要输出设备故障结论。若规则命中裸露导线、火花、烟火或积水附近电气设备，系统立即返回固定安全提示，并禁止生成自行拆修、接线或触碰建议。

Agent 继续收集位置、户号、联系方式和文字描述，生成报修草稿。只有用户二次确认后，才复用现有幂等动作机制提交模拟工单。

### 6.3 多模态 RAG

入库时为政策文档、流程图、App 截图和设备图片生成：原始文本、OCR 文本、视觉说明、页码/区域、缩略图、来源版本和向量。第一版可将 OCR 与视觉说明作为文字向量检索；第二版再引入 CLIP/SigLIP 一类图文共享向量。

查询时组合关键词、文本向量和图文向量，通过 RRF 融合，再由重排器选证据。回答引用必须落到 `source + version + page/region + assetId`，页面可高亮对应区域。模型不得引用没有进入上下文的图片。

当前 JSON 向量与内存扫描适合小型演示集；数据扩大后再迁移 pgvector 或专用向量库，并用评测结果证明迁移必要性。

### 6.4 语音

第一版采用“录音完成后上传”：浏览器录音 → 格式/时长校验 → ASR → 展示可编辑转写 → 进入原文本 Agent → TTS。转写文本是可审计的标准输入，用户可在触发动作前修正。实时双工通话放到后续版本，避免一开始同时处理打断、回声、流式状态和高成本连接。

### 6.5 图像生成

只开放低风险用途：用电安全宣传图、操作步骤插图和账单解释卡片。生成前使用固定模板和内容安全检查，生成后加可见标识并要求人工确认。以下用途禁止：伪造账单/缴费凭证、生成故障现场“证据”、替换知识库原图、制作可能被误认为官方通知的图片。

图像生成是独立异步任务，不拥有业务工具权限。学习本地生成技术时，可以用 Diffusers 实现 LoRA/ControlNet 实验，但实验服务不进入默认 Compose 的核心业务链路。

## 7. 模型适配层

业务代码只依赖以下接口，不直接依赖厂商请求格式：

- `OcrEngine`
- `VisionUnderstandingModel`
- `MultimodalEmbeddingModel`
- `SpeechRecognizer` / `SpeechSynthesizer`
- `ImageGenerator`

每次调用记录 provider、模型版本、提示词版本、Schema 版本、耗时、用量和结果状态。结构化输出必须做服务端 JSON Schema 校验；解析失败只允许有限重试，之后明确失败或降级，不返回伪造结果。

推荐演进：

1. 托管 VLM 完成账单 MVP，快速验证产品链路。
2. 增加 OCR 基线与评测对比，理解传统 OCR 和 VLM 的差异。
3. 增加 Python 推理侧车，使用 Transformers/vLLM 部署一个可替换的本地 VLM。
4. 用 Diffusers 单独完成图像生成实验，记录显存、吞吐和质量。

## 8. 安全威胁模型

| 风险 | 控制措施 |
| --- | --- |
| 图片中的提示词注入 | OCR/图片文字标记为不可信内容；系统提示隔离；结构化白名单输出；禁止由图片触发工具 |
| 越权读取附件 | 每次读取校验 `owner_id` 和角色；对象存储不公开；短时签名 URL |
| 图片炸弹/伪装文件/资源耗尽 | 魔数、像素和页数限制；解码超时；限流、配额、异步队列 |
| PII 泄露 | EXIF 清理、字段脱敏、日志禁原文、短保留期、删除任务 |
| 高风险电气建议 | 确定性安全规则优先；危险场景固定话术；禁止维修步骤；安全回归集 |
| 幻觉证据 | 只允许引用检索上下文；来源版本与区域可追溯；无证据时拒答 |
| 生成图片被当成事实 | AI 标识、溯源元数据、独立存储区、禁止进入业务证据链 |

## 9. 评测设计

### 9.1 数据集

先建立 30 条脱敏/合成的开发集打通评测程序，再扩展到 100—200 条冻结测试集。测试集与提示词调试集严格分离，以 JSONL 保存样本 ID、输入资源校验和、期望字段、证据区域、风险标签和人工标注版本。账单模板、清晰度、拍摄角度、遮挡、无关图片和对抗文本都要分层采样。

### 9.2 指标与建议门禁

| 能力 | 指标 | 首个可写入简历的门禁 |
| --- | --- | --- |
| 账单提取 | 关键字段 Exact Match | ≥ 95% |
| 金额识别 | 数值准确率 | ≥ 99%，冲突不得静默通过 |
| 无关图片 | 拒绝准确率 | ≥ 95% |
| 模糊图片 | 正确提示补充率 | ≥ 90% |
| 故障安全 | 高风险拦截召回率 / 危险维修建议数 | 100% / 0 |
| 多模态检索 | Recall@5 / 引用正确率 | ≥ 90% / ≥ 95% |
| 图片问答 | 人工评分或任务准确率 | ≥ 85% |
| 中文 ASR | CER | 按安静/噪声分层报告，不只报平均值 |
| 性能 | p50/p95 延迟、失败率 | 达到项目 SLO，并记录模型成本/显存 |

这些是个人项目的首版目标，不是行业承诺。正式评测前冻结样本、指标实现和阈值；每次报告包含模型/提示词版本、硬件、样本数、分层结果和失败案例，不能只展示一个最好平均数。

### 9.3 故障注入

至少覆盖模型超时、429、返回非 JSON、对象存储不可用、Redis 不可用、任务执行中服务重启、重复回调和数据库乐观锁冲突。验收重点是：不丢任务、不重复提交业务动作、能观测、能恢复或明确失败。

## 10. 可观测性与成本

新增指标按 `modality/task/provider/model/result` 聚合，禁止把 `userId`、户号和原始提示作为指标标签：

- 上传拒绝率、处理队列长度、各状态停留时间；
- OCR/VLM/ASR/TTS/生成调用量、错误率、p50/p95 延迟；
- 输入/输出 token、音频秒数、生成图片数、估算成本；
- 低置信度率、规则冲突率、人工修正率；
- RAG 证据命中率和无依据拒答率；
- 本地模型的 GPU 显存、利用率和吞吐。

为单次请求贯穿 `traceId → assetId → jobId → analysisId → actionId`，以便从界面结果追踪到模型版本和业务回执。

## 11. 分阶段交付

### M0：设计与评测骨架

- 定义 Schema、错误码、30 条开发集和离线评测命令。
- 完成标准：空实现也能运行评测并生成带版本的报告，失败项明确为未实现。

### M1：安全上传与资产生命周期

- 完成对象存储、数据库迁移、所有权校验、TTL 清理和重启恢复测试。
- 完成标准：越权、伪装文件、超限文件和重复上传测试通过。

### M2：账单图片最小闭环

- 完成 VLM/OCR 提取、Java 校验、前端纠错和账单解释。
- 完成标准：冻结集达到门禁，金额冲突不会进入 `VERIFIED`。

### M3：故障图片辅助报修

- 完成质量判断、现象提取、安全规则、槽位补全和确认提交。
- 完成标准：高风险拦截测试全通过，零危险维修指令。

### M4：多模态 RAG

- 完成图文入库、混合检索、区域引用和证据展示。
- 完成标准：检索与引用门禁通过，回答可回溯到原始来源。

### M5：语音交互

- 完成批量 ASR、转写确认和 TTS；之后再评估实时 API。
- 完成标准：噪声分层报告、动作前可纠错、超时有降级文本。

### M6：隔离的图像生成实验

- 完成宣传图/解释卡片、溯源、AI 标识、安全检查和人工确认。
- 完成标准：生成物不能进入账单、故障或知识证据表。

### M7：本地推理与性能实验

- 增加 Python 侧车、量化和 vLLM/Diffusers 实验，对比托管模型。
- 完成标准：报告精度、延迟、吞吐、显存与成本，而不是只证明“能启动”。

## 12. 学习路线与产出证据

阅读论文的目的要对应一次工程实验：

| 学习主题 | 要回答的问题 | 项目实验 |
| --- | --- | --- |
| ViT | 图片如何成为 patch token | 比较分辨率/裁剪对账单字段的影响 |
| CLIP | 图文如何进入共享向量空间 | 图片查文字、文字查截图的 Recall@K |
| LLaVA | 视觉编码器如何连接 LLM | 绘制本地 VLM 推理链并分析错例 |
| VAE/DDPM/LDM/DiT/Flow Matching | 图像生成的压缩、噪声与采样机制 | 固定提示词比较质量、步数、延迟、显存 |
| ControlNet | 如何加入空间条件 | 用边缘/布局控制一张宣传图，记录可控性 |
| Whisper | ASR 的统一序列建模 | 中文电力术语的 CER 与热词错例表 |
| VideoMAE/Omni | 视频/多模态时序如何建模 | 只做离线实验，不提前承诺生产功能 |

每个阶段至少留下：架构决策记录（ADR）、可运行代码、自动化测试、版本化评测集、机器生成报告和三类失败案例。面试时重点解释为什么这样设计、失败时如何降级，而不是背模型名词。

## 14. 技术资料的使用方式

- Transformers 的多模态 chat template 用于理解图片/音频/视频与文本如何组织为模型输入；业务层仍传统一的附件引用。
- Diffusers 用于独立的生成实验和 ControlNet 学习，不替代业务安全控制。
- vLLM 用于本地 VLM 的推理服务和吞吐实验，不负责业务权限、幂等或工作流。
- 模型 Model Card 用于确认输入限制、量化、显存、许可和已知风险；这些信息应写进具体适配器的 ADR，而不是硬编码在总设计中。

外部模型名称、上下文限制、价格和弃用日期会变化。实现时应以模型官方文档为准，并通过配置指定模型，不把易变信息写死在业务代码里。
